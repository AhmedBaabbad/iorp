## تقييم RLS

لا أوصي بتفعيله الآن. سياق الوصول الحالي تطبيقي، وهناك queries مشروعة عابرة للمنظمات في المنصة والجدولة. قبل أي اعتماد: تحديد دور DB للتطبيق والمنصة، عدم تسرب SET LOCAL عبر pool، ملكية التوابع، migration role وbypass، وسياسة الفشل دون tenant context. البديل الأول هو تقوية الاختبارات والعلاقات المؤكدة الخطورة. لا تغيرًا معماريًا كبيرًا دون قياس وتجربة.

## مراجع المنهج وليست شهادة امتثال

- [OWASP Multi-Tenant Security](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html): سياق موثوق وعزل الموارد؛ استخدم لتصميم اختبارات سلبية.
- [OWASP ASVS 5](https://github.com/OWASP/ASVS/tree/master/5.0): متطلبات تحقق المصادقة والتفويض والجلسات؛ لا ندعي اجتياز مستوى كامل.
- [OWASP API Security](https://owasp.org/www-project-api-security/): فحص الوصول إلى الكائن والوظيفة منفصلين.
- [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b/aal/): تقييم عوامل المصادقة والمقاومة للتصيد؛ TOTP لا يوصف بأنه مقاوم للتصيد ولا يكفي وحده لادعاء امتثال AAL2.
- [Azure Control Planes](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/control-planes): فصل مسؤوليات المنصة وتحديد التعافي والتشغيل.

## قرار المرحلة

Needs Revision قبل اعتماد التشغيل متعدد الشركات المستقلة. هذا ليس حكمًا بأن العزل كله مكسور؛ فصل الهوية موجود مع نقاط قوة واضحة. بوابة الإطلاق: إغلاق F01–F06، تفسير كل اختبار فاشل، وتوثيق مخاطر P1 المقبولة صراحة.
