# خطة التقوية التدريجية

2026-10-14 — مقترحة للاعتماد؛ لم تبدأ تعديلات التطبيق. مصدر بوابة الاعتماد: نص المهمة، Step D: “Do not begin code modifications until the assessment and proposed plan have been reviewed and approved.”

## الحزمة A — تثبيت خط الأساس والعزل (P0)

1. حفظ نتائج الاختبارات الحالية وتصنيف الفشل إلى عيب منتج أو اختبار عقد قديم؛ لا إخفاء الفشل بتغيير التوقع فقط.
2. جرد endpoints للـtenant مع مصدر organization_id وملكية المعرفات التابعة والصلاحيات، وربطها باختبارات A/B.
3. تشمل الملفات والتقارير والبحث والتصدير وheaders/query/body/path، مع حسابين محدودين وجذرين اختباريين لاختبار الفرق بين tenant isolation وpermission scope.
4. مراجعة scheduler وservice cache وحدود المعاملة؛ لا تعديل business rules.
5. تشغيل SQLite السريع وPostgreSQL المعزول للقيود والأقفال. أتمتة المجموعة في CI عند تحديد بيئة تشغيلها.

القبول: لا وصول عابر مثبت، وكل نقص تغطية موثق وحرج مغلق. لا استخدام ريحانة أو المتحدة كfixtures.

## الحزمة B — الجلسات والمعاملات الإدارية (P0)

- F01: session_active لمنصة الإدارة، اختبار logout ثم إعادة استخدام access؛ الحفاظ على عقود JWT والتحقق من الجمهور والمصدر.
- F02: نقل commit إلى حد عملية واحد في دورة حياة المنظمة؛ audit والجلسات والحالة معًا. اختبار rollback وتزامن انتقالين على PostgreSQL.
- F03: تدقيق حصة التخزين ذريًا ويمر بالفاعل المعتمد؛ لا queries business من Platform.
- فحص الإنشاء واستعادة الجذر: البريد أثر خارجي لا يُعاد rollback له، لذلك تسجيل نية/نتيجة أو نمط إرسال موثوق حسب الموجود، دون ادعاء atomicity مع SMTP.

القبول: حقن فشل audit، فشل SMTP، retry؛ لا تغير ناجح بلا سجل ولا تكرار غير مقصود. ترحيل فقط إن أثبتت الحاجة وبعد جرد caller contracts.

## الحزمة C — MFA وحماية المسؤولين (P0)

اختيار مكتبة مدققة لا خوارزمية تشفير مصنوعة محليًا. اختبار ملاءمة WebAuthn/passkeys لبيئة HTTPS؛ عند البدء بـTOTP يحفظ السر مشفرًا بمفتاح تشغيل منفصل، وتجزّأ recovery codes وتستخدم مرة واحدة. تسجيل أول عامل يتطلب كلمة مرور حديثة؛ تعطيل/استبدال العامل يتطلب عاملًا قائمًا أو recovery مضبوطًا. enrollment-pending لا يمنح صلاحيات Platform كاملة. reset password لا يمحو MFA. تحدي MFA قصير العمر ومحدود المحاولات وغير قابل للإعادة.

تضاف migration وUI عربية/إنجليزية فقط لهذا الغرض. سياسة configurable للمهلات وstep-up للأرشفة وتعليق منظمة وتغيير صلاحيات مسؤول. خطة bootstrap/recovery قبل الإلزام لتجنب فقدان الإدارة؛ لا secret ظاهر في logs. لا تعدد أدوار تجاري جديد.

## الحزمة D — التعافي والنشر (P0)

- حصر PostgreSQL والملفات والأسرار اللازمة لفك النسخ وحفظها خارج الجهاز وبصلاحيات منفصلة.
- إعداد backup والتحقق من سلامته ثم استعادة إلى قاعدة ومسار ملفات مؤقتين؛ مقارنة بيانات اختبار وفتح مرفقات اختبار.
- توثيق RPO/RTO المقاسين، لا أرقام تقديرية بوصفها ضمانًا. لا اعتماد restore لمنظمة منفردة قبل إثبات خريطة العلاقات؛ لا حذف/merge فوق الإنتاج.
- تحقق app_env، HTTPS، trusted proxies، CORS، cookies، docs policy، رسائل الأخطاء، dependency audit حديث وCI.

## الحزمة E — تحسينات محدودة بعد اجتياز P0 (P1)

F07–F11: صلاحية استرداد مستقلة، أسباب القرارات، pagination وتجميع counts؛ قياس query counts. مؤشرات زمن API وأخطاء ونجاح jobs وحصة التخزين دون payload أعمال. تقييم قيود DB المرشحة بعد اختبار العزل؛ لا RLS تلقائي.

## إدارة التغيير

لكل حزمة diff محدود، اختبارات رفض وإيجاب، ملف نتائج، خطة rollback أو forward recovery. لا migrations هدامة دون موافقة مستقلة. تبقى الوحدات التشغيلية والبيانات والمعرفات والحالات الصحيحة كما هي. معيار انتهاء كل حزمة هو الدليل التنفيذي، وليس التقرير أو نجاح typecheck وحده.

## المطلوب اعتماده الآن

اعتماد A وB كبداية صغيرة قابلة للمراجعة. C وD مطلوبتان قبل الإطلاق لكن تُراجع تفاصيل تنفيذهما بعد نتائج A/B. لا تنفيذ P1 أو P2 ضمن هذه الموافقة. يمكن اعتماد ترتيب مختلف صراحة؛ لا يعني طلب التقرير اعتماد التعديلات تلقائيًا.
