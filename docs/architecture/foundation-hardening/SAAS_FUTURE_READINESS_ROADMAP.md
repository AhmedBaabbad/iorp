# خارطة الجاهزية المستقبلية كمنصة SaaS — IORP

**التاريخ:** 2026-10-14 · **للتوثيق فقط — لا تنفيذ، ولا جداول أو خدمات أو شاشات تخمينية.**

## نقاط الامتداد الموجودة فعلًا (تُبنى عليها لاحقًا)
| الامتداد | الموجود اليوم | كيف يُستفاد منه |
|---|---|---|
| إعدادات خاصة بكل منظمة | `Organization` (لغة، منطقة زمنية، `storage_quota_bytes`، `max_sessions_per_user`)، جداول إعدادات لكل وحدة (`*_settings`) | الخطط تضبط هذه القيم بدل أعمدة جديدة مبعثرة |
| حصص | `core/files.py usage/quota/store` | نمط «استهلاك مقابل حد» يُعمَّم على المستخدمين والوحدات |
| صلاحيات دقيقة + كتالوج | `foundation/domain/permission_catalog.py`، أدوار نظام | تفعيل وحدة = إتاحة صلاحياتها؛ إيقافها = حجبها مركزيًا |
| واجهات بين الوحدات | `app/core/interfaces/*` | أي وحدة اشتراكات/فوترة تكون وحدة مستقلة تتصل عبر واجهات |
| دورة حياة المنظمة | آلة حالات `platform/domain/policies.py` | الحالة التشغيلية تبقى منفصلة عن حالة الاشتراك والدفع |
| التدقيق والإشعارات | `PlatformAuditService`، `core/interfaces/notifications` | أحداث الاشتراك والفوترة تستخدمها كما هي |

## الفصل المفاهيمي (يُحترم عند البناء)
- **الحالة التشغيلية** (active/suspended/…) ≠ **حالة الاشتراك** (trial/active/past_due/cancelled) ≠ **حالة الدفع** ≠ **الاستحقاقات** (وحدات، حدود). لا يُخلط أي منها في عمود الحالة الحالي.

## مخاطر مستقبلية يجب تذكرها
1. الجداول الفرعية بلا `organization_id` تجعل التصدير/RLS/الحذف لمنظمة واحدة أصعب — أي جدول **جديد** مملوك للمنظمة يجب أن يحمل `organization_id` (قاعدة تصميم).
2. تفرّد البريد عالميًا يعني أن الشخص لا ينتمي لمنظمتين بنفس البريد — قرار يُراجع إن ظهرت حاجة.
3. المهام الخلفية داخل عملية الويب تمنع التوسع الأفقي دون قفل موزّع.
