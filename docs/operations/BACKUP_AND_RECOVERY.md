# النسخ الاحتياطي والاستعادة — إجراء آمن

التشغيل المجدول ورفع Drive وإجراءات المالك موثقة في [BACKUP_OPERATIONS.md](BACKUP_OPERATIONS.md).
المرحلة هـ تستخدم تحقق استعادة يوميًا من النسخة المنزّلة، دون نافذة تجميد في v1؛ تعيد الجمع مرة واحدة عند مراجع ملفات مفقودة.
scratch خاص على القرص ومؤقت، حسب تعديل التصميم المعتمد؛ توصيات التشفير/RAM الأقدم أدناه تخص الخيار السابق ولا تعطل حراسات هوية وجهة الاستعادة.
production تظل معطلة حتى نجاح طرح staging ومراجعة Claude. المحتوى التاريخي التالي يوضح أدلة ومحددات الجولات السابقة، ولا يثبت تفعيل الجدولة.

## تحديث الدفعة 1.5

أداة `backend/scripts/backup/iorp_backup.py` خضعت الآن لتصحيحات واختبار فعلي على خادم PostgreSQL اصطناعي مستقل:

- في وضع التشفير، يمر خرج pg_dump وأرشيف الملفات مباشرة إلى تدفق التشفير؛ لا تكتب نسخة plaintext في مجلد النسخ أولًا. يبقى `--no-encrypt` خيارًا صريحًا غير مناسب لنسخة إنتاج حساسة.
- التحقق لا يستخدم إعداد قاعدة التطبيق افتراضيًا. يلزم `IORP_RESTORE_DATABASE_URL` لهدف اختبار مستقل، ويبدأ اسم قاعدة الاتصال بـ `iorp_restore_verify_`. ينشئ التحقق قاعدة جديدة بهذا النمط ويرفض الموجودة واسم قاعدة المصدر. الاسم حارس ضد الأخطاء، وليس إثباتًا أن الخادم غير إنتاجي؛ يجب التحقق من host/port قبل التشغيل.
- يلزم `IORP_RESTORE_SCRATCH` لمجلد مخصص على قرص مشفر أو RAM-backed. فك التشفير والاستعادة يحتاجان مساحة plaintext؛ لا يمكن للأداة إثبات تشفير القرص، ولا نضمن المسح الآمن من SSD. لا تستخدم مجلد النظام المؤقت افتراضيًا.
- يفحص `prune` سلامة كل الأرشيفات قبل أي حذف، ويرفض الاحتفاظ إذا كانت أحدث نسخة بلا سجل استعادة ناجح مطابق لبصمة manifest. يحافظ دائمًا على أحدث نسخة متحقق منها حتى مع سياسة 0/0/0. هذا السجل دليل تشغيلي محلي وليس توقيعًا ضد مهاجم يملك تعديل ملفات النسخ.
- الاستخراج يرفض الوجهة الموجودة والروابط ومسارات الخروج. فحوص أداة `recovery_drill.py` أصبحت استثناءات صريحة لا تختفي مع `python -O`.

لإعادة تمرين الأداة المشفرة على بيانات اصطناعية فقط، من backend وبنفس متغيرات البيئة الآمنة المذكورة في تقرير الدفعة:

```powershell
$env:RUN_BACKUP_CONTAINER_TESTS='1'
python -m pytest tests/test_backup_roundtrip_isolated.py -q
```

الاختبار ينشئ حاويته الخاصة بمنفذ loopback عشوائي ثم يحذفها، ولا يقرأ رابط قاعدة التشغيل. لا يثبت اكتمال نسخ الإنتاج. قبل تفعيل النسخ الإنتاجية يجب اعتماد خادم استعادة منفصل، تخزين نسخة مشفرة خارج المضيف، مخزن مفتاح منفصل، مراقبة عمر النسخة، ونافذة اتساق الملفات مع قاعدة البيانات. لا تغييرات نشر أو جدولة إنتاجية ضمن هذه الدفعة.

## ما نُفذ الآن

أداة تطوير `backend/scripts/recovery_drill.py` تنشئ PostgreSQL 16 جديدًا بلا منافذ منشورة، بلا شبكة، وبلا ربط مجلدات العمل. لا تقرأ رابط قاعدة التشغيل. تنشئ بيانات اصطناعية، تنسخ قاعدة البيانات بـ pg_dump بصيغة custom، وتؤرشف مرفقات اصطناعية، وتحسب SHA-256. تستعيد الأرشيف المصدر إلى قاعدة جديدة وتتحقق من النتائج والمرفقات. وجهة الملفات يجب ألا تكون موجودة؛ تُرفض مسارات الأرشيف الخارجة والروابط. لا خيار لاستهداف خادم قائم.

من جذر المستودع، مع Python الذي يحتوي اعتماديات backend وDocker متاح:

```powershell
python backend/scripts/recovery_drill.py --application-schema --output .tmp/recovery-new-run
```

استخدم مجلد نتائج جديدًا لكل تشغيل. الخيار application-schema يحمل تعريفات ORM دون تشغيل التطبيق أو فتح قاعدة التشغيل. وهو **لا يختبر سلسلة Alembic** ولا يعوض استعادة بيانات الأعمال كاملة. manifest للتحقق من التلف، وليس توقيعًا يمنع عبث مهاجم بالنسخة وبالـmanifest معًا. النسخ هنا غير مشفرة لأنها اصطناعية فقط، ولا يجوز استخدامها لحفظ نسخة إنتاج حساسة بهذه الصورة.

## الدليل الحالي

الجولة الحالية: PostgreSQL 16.11، استعادة 119 جدولًا (مخطط ORM مع جداول التمرين)، منظمتان اصطناعيتان في جداول التمرين، مستندان ومرفقان. زمن جزء الاستعادة 6.297 ثانية، والزمن الكلي 32.219 ثانية. هذه أزمنة بيانات صغيرة على جهاز التطوير، **ليست RTO للإنتاج**. لم تُنسخ بيانات ريحانة.

## إجراء النسخ التشغيلي المقترح — لم يُفعّل

يتطلب تنفيذًا منفصلًا مصرحًا به على الخادم:

1. تحديد مالك النسخ، موضع PostgreSQL الفعلي ومجلد التخزين من إعدادات النشر، وحفظ مفاتيح الاسترداد والإعدادات السرية في مخزن أسرار منفصل.
2. تحديد RPO/RTO مع صاحب النظام؛ اقتراح أولي RPO لا يتجاوز 24 ساعة، وليس ضمانًا قبل الجدولة والمراقبة. أحجام البيانات تحدد RTO المقاس.
3. للحصول على اتساق DB مع الملفات: نافذة صيانة قصيرة توقف الكتابة والجدولة والمهام الخلفية، ثم pg_dump مع نسخ ملفات التخزين في النافذة نفسها؛ أو snapshot متسق مع بروتوكول موثق. pg_dump وحده لا يضمن اتساق المرفقات المتغيرة.
4. استخدام حساب نسخ بأقل صلاحية مناسبة، pg_dump متوافق، وأسماء أرشيف فريدة. لا كلمات مرور في سطر الأوامر أو Git. فشل أي جزء يعني أن النسخة غير مكتملة.
5. تشفير النسخة بأداة معتمدة مع حفظ المفتاح منفصلًا، ونقل نسخة خارج الجهاز بحساب محدود وسياسة احتفاظ معتمدة. لا حذف تلقائي للنسخ السابقة قبل التحقق من الجديدة.
6. تسجيل الحجم والبصمة وإصدار PostgreSQL ومعرف إصدار التطبيق وAlembic، وتنبيه المسؤول عند الفشل أو غياب آخر نسخة متوقعة.
7. اختبار استعادة دوري على خادم مستقل لا يتصل بالبريد أو المدفوعات أو المستخدمين؛ قاعدة جديدة لا تحتوي بيانات، ملفات بوجهة جديدة، تحقق من checksum ثم pg_restore مع exit-on-error ومعاملة واحدة.
8. مطابقة أعداد وسلامة العلاقات بين بيانات الأعمال والمنظمات والمرفقات ونسخة Alembic، ثم smoke tests للطلبات والإنتاج والجودة والشحن والتقارير بحسابات اختبار. لا نشر النسخة المستعادة تلقائيًا.

## حدود الاستعادة والتعافي

لا تستعد نسخة إلى قاعدة التشغيل للاختبار. لا تستخدم DROP أو clean لاستبدال بيانات قائمة. استعادة منظمة منفردة من قاعدة مشتركة تحتاج خطة منفصلة لضمان كل العلاقات، ولا تنفذ بنسخ صفوف يدويًا إلى الإنتاج. يلزم اعتماد منفصل قبل أي استبدال إنتاجي، مع نقطة رجوع ووقت توقف معلوم.

**غير منفذ:** الجدولة الإنتاجية، النسخ الخارجية والتشفير وإدارة مفاتيحه، اختبار نسخة واقعية، اختبار سلسلة migrations في هذا التمرين، قياس RPO/RTO للإنتاج، استعادة منظمة منفردة. توفر الأداة اختبارًا فعليًا للآلية ومخطط ORM، وليس إعلان جاهزية التعافي التشغيلي.
# Restore destination gate (2026-10-14)

Restore verification now requires `APP_ENV=test`, a disposable local Docker container
labelled `iorp.purpose=backup-test`, and `IORP_RESTORE_CONTAINER_ID` set to its full
64-character ID returned by `docker run`. Pass that container to `--docker-container`.
`IORP_RESTORE_DATABASE_URL` must use its inspected `127.0.0.1` published PostgreSQL
port, with no connection query overrides. Remote Docker endpoints, endpoint environment
overrides, bind mounts, mismatched IDs/ports and missing evidence are rejected before
connecting to PostgreSQL. Existing scratch/encryption/database-name safeguards still apply.
The opt-in `tests/test_backup_roundtrip_isolated.py` provisions and checks this destination.
This intentionally restricts restore drills; it does not change production backup collection.
